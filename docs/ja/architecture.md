# 設計

refrain の今の組み立てと、守っている規則を書きます。機能が増えるのに合わせて書き足します。

## 2 つのスレッドと、それぞれの規則

```
UI・制御のスレッド ──(lock-free キュー)──▶ オーディオスレッド
  デバイス、ファイル、プラグインの画面          トランスポート、グラフ、プラグインの process()
  確保・ロック・待ちをしてよい                  確保・ロック・待ち・I/O をしてはいけない
```

オーディオスレッドには締め切りがあります。48 kHz・128 フレームのブロックなら、毎回約 2.7 ms で
終えなければなりません。間に合わないと、プツッという音になって聞こえます。そのため、
オーディオスレッドで動くコードは次のことをしません。

- メモリの確保と解放
- もう一方のスレッドが持つかもしれないロックを取ること
- I/O、print、待ち

メモリは `Processor::prepare` で確保します。これはオーディオスレッドの外で、最初のブロックの前と、
サンプルレートが変わったときに呼ばれます。

## crate

### `refrain-engine`

エンジンです。OS、デバイス、ファイルのコードを持たず、依存もありません。

- `Processor` は、インターリーブされた `f32` のバッファを埋めるものです。
  `prepare(sample_rate)` を呼んだあと、`process(out, channels)` を繰り返し呼びます。
- `render_offline` は、デバイスを使わずに `Processor` を動かします。デバイスと同じように、
  指定した大きさのブロックに分けて呼びます。

### `refrain`

`refrain` コマンドです。OS に触れる部分はすべてここが持ちます。

- オーディオデバイス: `cpal` を使う（macOS は CoreAudio、Windows は WASAPI）
- WAV ファイル: `hound` を使う

デバイスが `f32` 以外のサンプル型を求めてきたときは、コールバックの中に持たせた固定長のバッファに
エンジンの出力を書き、そこから変換します。そのため、この場合もオーディオスレッドは確保をしません。

## デバイスを使わない経路が大事な理由

CI のマシンにはサウンドカードがありません。そこで、エンジンは `render_offline` を通して検査します。
この経路にもデバイスと同じ規則を課しています。

- **出力はブロックの大きさによらない。** 1、64、128、480、1000 フレームのどのブロックで書き出しても、
  サンプルはビット単位で一致します。ブロックの大きさはデバイスが決めるので、それで変わるものは
  バグです。

## OS ごとのコードは薄く保つ

macOS と Windows で違うものは、すべて外側に置きます。オーディオデバイス、MIDI ポート、
プラグインの画面のウィンドウハンドル（`NSView` と `HWND`）、プラグインを探す場所です。
エンジン、グラフ、トランスポート、プロジェクトファイル、プラグインのホスト機能の大部分は共通です。
